Sealtrace — a notary that never sees your evidence

A weekend invention: what's the smallest honest tool that lets someone document a scam or harassment message well enough to be believed later — without asking them to trust a server, make an account, or hand their evidence to a company?

Context

FakeAlert (my other flagship project here) tries to catch disinformation and hate speech automatically. Sealtrace starts from the opposite end of the same problem: the moment after a person has already been targeted — by a phishing message, a scam impersonating their bank, a harassing DM, a doctored screenshot circulating about them — and needs someone else (a platform, a bank's fraud team, a moderator, a friend) to believe what they're showing them. That's a documentation and trust problem, not a detection problem, and I hadn't seen a tool that treated it as its own design space.

The problem

Screenshots are the default evidence format for digital harm, and they're weak in a specific way:

  • They're trivially editable. Anyone can be told "that's photoshopped," and often they're right to be skeptical — there's no way to tell from the image alone.
  • Formal chain-of-custody tools don't fit. Forensic evidence software is built for investigators with case management systems, not for someone forwarding a scam text to a bank's support inbox tonight.
  • "Just trust our server" isn't good enough. The obvious fix — upload the image to a service that timestamps it — asks the victim to trust a company with exactly the sensitive material they're trying to prove is sensitive, and it dies the day that company does.

Goals & constraints

  • Zero trust in me. No upload, no account, no server call — I shouldn't be able to see anyone's evidence even if I wanted to.
  • Zero install. A static HTML page, exactly like the rest of this site — open a link and use it.
  • Verifiable by anyone, forever. A recipient with no relationship to Sealtrace should be able to check a capsule's integrity from the file alone, offline, years later.
  • Honest about what client-side crypto can't do. This is the constraint that shaped the whole design — see below.

The design problem client-side tools can't dodge

A single self-contained HTML file that embeds an image and a hash of that image can verify internal consistency — "does this file's image match the hash printed in this same file?" — but it cannot, by itself, prove when it was made or that it wasn't quietly regenerated later with a different image and a matching new hash. Anyone who can edit a file can edit both halves. A lot of "proof" tools quietly skip over this and let the packaging feel more authoritative than it is. I wanted Sealtrace to be honest about it instead of hiding it.

The fix doesn't require a server — it requires one step happening outside the tool entirely: publish the hash somewhere you don't control, before you hand the capsule to anyone. A forum reply, a public commit, a text to a friend — anything with an external, independently-checkable timestamp. Once that hash is out in the world, the capsule can't be quietly regenerated without the mismatch showing. Sealtrace's actual contribution isn't the hashing (that part is standard); it's making that one external step a first-class, one-click part of the workflow instead of an afterthought nobody does.

Architecture

Seal

SHA-256 + perceptual hash computed locally per image.

Redact

Optional — destructive blackout, with a pre-redaction hash commitment kept.

Chain

Items combined into one Merkle root so order can't be reshuffled.

Anchor

Root posted publicly — the one step outside the tool's control.

Verify

Capsule re-hashes itself on open, in any browser, forever.

Notable design decisions

Nothing to leak, because nothing is sent

There is no fetch() or XMLHttpRequest anywhere in the codebase. Hashing runs on-device via crypto.subtle; the exported capsule's self-check reads its own embedded data: URIs, which never touch a network. A person with something to hide from a platform doesn't have to hide it from me either.

Redaction that's actually destructive

Before a blackout box is drawn, the tool hashes the pixels underneath it and records that hash — then overwrites those pixels in the working canvas. The original bytes are never exported and never sit in memory as a keepable copy; only a commitment to "something existed here, and it hashed to X" survives, so a redaction can't be silently thin (a transparent box someone forgets to flatten) or falsely claimed as more extensive than it was.

A Merkle root for the boring reason

Real incidents are usually more than one screenshot — a conversation, a sequence of messages. Hashing each image alone doesn't stop someone dropping message 3 or reordering the conversation. A Merkle root over the items, in order, does — for the same reason a git commit history resists silent reordering.

What I deliberately did not claim

It would be easy to oversell this as "cryptographically proven evidence." I didn't want to, because it isn't, and evidence tools that overclaim are worse than none:

  • It cannot prove the original screenshot wasn't already faked before sealing — Sealtrace attests to "this is what was sealed," not "this is what really happened."
  • Without the anchor step, the timestamp is only as trustworthy as the device it was made on.
  • Perceptual hashing (used to flag likely-the-same image across re-compression) is a similarity signal, not an identity proof, and is documented as such in the UI.

The honest pitch is narrower and, I think, more useful: a free way to make a screenshot harder to dismiss out of hand, with the gaps stated up front rather than discovered under cross-examination.

What's next

  • A "verify an existing capsule" mode that re-checks a capsule someone sends you, without needing the original Sealtrace session.
  • Optional OpenTimestamps-style anchoring for people who want a stronger, automatic external timestamp than a manual public post.
  • A short guide for platforms and support teams on how to read a Sealtrace capsule's verification banner.

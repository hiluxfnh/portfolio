Haven — support routing without a black box

This page exists because an earlier version of this portfolio described a project that didn't exist yet: an "AI chatbot" for legal resources, mental-health support, and incident reporting. Haven is the honest, shipped replacement — and the story of why its scope shrank on purpose.

Context — and a correction

While auditing this whole site for gaps, I found a project card describing an "Open-Source AI Chatbot" consolidating legal resources, mental-health support, and incident reporting via Hugging Face Transformers on a Flask/Docker backend. Its "View code" link went to my GitHub profile root — there was no repository behind it. It was the one project on the site that read as real but wasn't, and it needed either a real build or an honest correction. This is the real build.

Why the original scope was the wrong scope

The original description was a plausible tech stack for a plausible idea, but the idea itself was riskier than it looked once I actually sat down to build it. A chatbot that gives NLP-driven advice to someone in crisis has to be right — a wrong or subtly-off response to someone describing abuse or suicidal thoughts is not a bug you patch later, it's a harm you've already caused. Building that responsibly needs domain review, safety testing, and ongoing maintenance that a single portfolio project can't honestly promise.

So I changed the question from "how do I build the chatbot that was described" to "what is the smallest thing I can build today that is actually safe and actually helps?" The answer was: stop trying to understand the user at all, and just get them to the right door faster.

What Haven actually does

You select from a fixed list of situations — harassment, a scam, emotional distress, gender-based violence, or just wanting to document something. There's no free-text box, no model reading what you type, nothing to classify. Each situation maps to a fixed, ordered list of resources through a plain lookup table in haven-core.mjs — the same file the Node test suite runs against, so the mapping is both inspectable and tested.

Notable design decisions

Deliberately not "cutting-edge NLP"

The rejected version's biggest selling point — an NLP model reading free text — was also its biggest liability. A rule table can't misread a crisis; it can only be incomplete, and incompleteness is something a reader can see and I can fix, unlike a model's internal reasoning.

Only resources I could verify

Crisis and abuse resources link to Find A Helpline, Befrienders Worldwide, and the IASP Crisis Centres directory — established, actively-maintained international directories. I deliberately did not hand-type a specific hotline number anywhere: an AI-generated crisis number that's wrong or outdated is exactly the kind of harm this project exists to avoid.

Reusing what already exists

"Incident reporting" from the original pitch already has a real answer on this site: Sealtrace, which seals evidence entirely client-side. Rather than rebuild that inside a chatbot, Haven just points there. The scam/phishing path points at PhishBlock the same way.

What I deliberately left out of v1

  • Free-text input of any kind — reintroducing it would reopen the exact risk this design avoids.
  • Country-specific hotline numbers — these change, and getting one wrong is worse than not showing one.
  • "Legal resources," as originally pitched — jurisdiction-specific legal aid is too easy to get confidently wrong from outside that jurisdiction; a future version should source this from a vetted directory the way the crisis resources are, not from me typing organisation names in.

What's next

  • A vetted legal-aid directory integration, once I find one with the same verification bar as Find A Helpline.
  • Localised resource ordering (e.g. prioritising Cameroon- or Russia-relevant directories) without ever inferring location automatically.
  • A short accessibility pass with screen-reader users, given who this is built for.
